# Журнал замеров производительности

Сюда пишется каждая попытка оптимизации — и принятая, и откаченная. Смысл
журнала в откаченных: они не оставляют следа в истории git, и без записи та же
мёртвая идея всплывает заново через полгода.

Правило одно: **нейтральная правка — это откат, а не «пусть полежит»**.
Сложность, за которую не заплатили измеримым выигрышем, обслуживается вечно.

## Как мерить, чтобы числа были сравнимы

Замер до и после делается одной командой в одних условиях. Для отрисовки —
пять прогонов в настоящем браузере, медиана, эмуляция медленного 4G
(1,6 Мбит/с, задержка 150 мс) и процессор вчетверо медленнее:

```bash
# на собранном проде, не в dev: npm run build && npx next start -p 4311
node -e "…puppeteer, Network.emulateNetworkConditions, 5 прогонов, медиана…"
```

Лабораторный PageSpeed по боевому адресу — вторая опора, но у него свой шум,
и сравнивать с ним локальные числа нельзя.

## 30.09.2026 — встроенные стили вместо внешнего файла

**Симптом.** PageSpeed mobile по `/en`: два файла стилей блокируют отрисовку,
оценка экономии 580 мс. Дело не в размере — 178 КБ под brotli это около 28 КБ,
— а в лишнем круге: браузер тянет HTML, находит в нём `<link>` и только потом
идёт за стилями.

**Правка.** `experimental.inlineCss: true` в `next.config.ts`. Стили уезжают в
`<style>` внутри HTML.

**Замер, пять прогонов, медиана FCP:**

| вариант | прогоны, мс | медиана |
|---|---|---|
| было, `<link rel=stylesheet>` | 1184 · 1204 · 1216 · 1248 · 1284 | **1216** |
| стало, `inlineCss` | 508 · 512 · 520 · 520 · 780 | **520** |

**−696 мс, то есть −57%.** Разброс базы ±50 мс, у правки 508–520 плюс один
выброс 780. Выигрыш многократно перекрывает шум.

**Цена.** HTML главной по сети: 84,6 КБ → 172,7 КБ gzip, плюс 88 КБ на каждый
просмотр. Стили теперь приезжают с каждой страницей и не кэшируются отдельно.
Считали, подходит ли размен: CSS атомарный и маленький, HTML и так лежит в
кэше ISR на краю сети, а аудитория приходит из поиска и в основном впервые —
именно ей кэш прошлого визита ничего не даёт. По трафику 88 КБ × 100 000
просмотров это 8,8 ГБ в месяц при включённом терабайте.

**Вердикт: принято.**

**Чего проверка НЕ показала и за чем следить:** правка увеличивает вес каждой
страницы, а у нас потолок Vercel упирается в число запросов, не в трафик.
Если счёт за следующий период вырастет по строке трафика заметнее, чем на
эти 8–9 ГБ, причину искать здесь.

## Бюджеты

Проверять при работе над скоростью. Превышение — повод открыть журнал, а не
молча оптимизировать.

| Что | Потолок | Откуда цифра |
|---|---|---|
| FCP, медиана, медленный 4G | 700 мс | текущее значение 520 мс, запас на рост |
| LCP, PageSpeed mobile | 2,5 с | порог «хорошо» Core Web Vitals |
| CLS | 0,1 | то же; сейчас 0 |
| HTML страницы по сети, gzip | 200 КБ | текущая главная 173 КБ |
| Блокирующих отрисовку запросов | 0 | стало после правки 30.09 |

Полевых данных CrUX у домена пока нет — трафика не хватает для выборки. Пока
их нет, лабораторные числа единственная опора, и относиться к ним надо как к
сравнению вариантов между собой, а не как к тому, что видят люди.
